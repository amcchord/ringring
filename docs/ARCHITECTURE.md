# Architecture

## System shape

RingRing deliberately starts as a small, self-hostable system:

```text
Internet
  |
  +-- HTTPS 443 -------------------- Caddy ---- RingRing web app ---- SQLite
  |
  +-- SIP 5061/TLS ----------------- Asterisk
  +-- SIP 5060/UDP (compatibility) --+
  |                                     |  ^
  +-- RTP 10000-10199/UDP --------------+  |
                                            |
                            generated config + private AMI reload
                                            |
                                       RingRing app
```

Caddy, the app, and Asterisk run as separate containers. Only Caddy's HTTPS port and Asterisk's SIP/RTP ports are public. The database, Asterisk Manager Interface (AMI), app origin, FastAGI service, and AI AudioSocket bridge stay on private container networks.

The app also owns a distinct loopback-only metrics listener on `127.0.0.1:9090`. Its scrape computes aggregate database/AMI/contact health and exports bounded process-lifetime web, reconciliation, and voice-service counters. Fixed label allowlists prevent family record values or caller input from becoming time-series dimensions. Compose does not expose or publish the port, Caddy never routes this listener, and RingRing includes no collector or remote-write destination. See [Privacy-preserving observability](OBSERVABILITY.md).

## Domain model

- **User**: an adult host with a RingRing-native account; optional federated login can be added without changing party ownership.
- **Party**: the hard tenant and dialing boundary. It owns an extension range and optional voice-service settings.
- **Host**: a user's administrative role in a party.
- **Invitation**: a single-use, expiring, hashed bearer token that permits one member/device enrollment.
- **Member**: a person represented by a display label and one extension within a party. An account is not required.
- **Device**: a SIP registration identity and encrypted secret associated with a member.
- **Provisioning link**: a single-use, 30-minute, hashed bearer token that lets one trusted phone app fetch only one device's account configuration.
- **Service line**: a party-enabled special extension such as time, weather, radio, or OpenAI voice.

## Call isolation

Every registered endpoint has a globally unique, random SIP username and an Asterisk endpoint context derived from its party ID. New credentials use a nonzero 6-digit username and a nonzero 12-digit password (about 39.7 bits of secret entropy), generated uniformly from the operating system CSPRNG. SQLite rejects a duplicate username and the application makes a bounded retry, so the shorter 900,000-value identity space cannot silently alias another phone. Numeric-only fields avoid keypad input-mode changes and the password remains machine-generated rather than a user-chosen PIN. The generated dialplan emits only that party's members and enabled service extensions into the context. There is no route from party contexts to trunks or a global outbound context.

Extension `101` can therefore exist in many parties without collision. A device cannot choose its context or construct a cross-party endpoint name.

A member may have several phones on one extension. The host-only add-device transaction requires the exact party, host, and member together, caps the member at eight saved devices, creates a new random SIP identity and encrypted password, and issues a distinct one-use provisioning token without rotating any existing phone. The renderer expands only that party member's active endpoints into one explicit `Dial(PJSIP/device-a&PJSIP/device-b,30,G(rr-party-bridge^s^1))` destination. Each phone can be tested, rotated, or revoked separately; a disconnected endpoint is omitted on the next reconciliation.

An answered member call moves its two original PJSIP channels into a private ConfBridge room named only from the validated party ID and originally dialed extension. Both original phones are marked owners; `end_marked_any` removes every later joiner when either owner hangs up, preserving ordinary call ownership. A generated exact route such as `*16102` may join only the corresponding `102` room from an already authenticated endpoint in that same party. The route confirms that the room still has at least two parties, asks FastAGI to resolve the joining endpoint to its same-party member, and never trusts caller ID or a caller-supplied conference name. ConfBridge recording is explicitly disabled, media stays server-relayed, and CDR is disabled for the conference legs.

The authenticated host phone book polls a no-store HTML fragment every three seconds. The app reads ConfBridge rooms and participants over private AMI, immediately reduces PJSIP channel names to active same-party members, and renders display labels, phone count, and the fixed join code only. Non-RingRing rooms, Local/announcement channels, cross-party rooms, stale extensions, unknown endpoints, caller IDs, channel IDs, timestamps, and network details are dropped. The browser pauses replacement while the page is hidden or a phone-book control is focused/open; the core page remains fully server-rendered and usable without JavaScript.

Before a later phone enters, FastAGI asks the party OpenAI project to synthesize the fixed sentence `Ring ring! {display name} is joining the party.` The name comes from the authenticated endpoint-to-member lookup. Caller audio is never sent to OpenAI. The name-bearing WAV uses a random filename with no member identifier, remains mode-restricted derived state, and is removed after one minute; startup also sweeps any copy left by an interrupted process. An unavailable party voice uses a bundled beep without blocking the join. AMI can originate only a fixed Local channel, fixed Playback application, validated RingRing conference, and allowlisted playback path.

The public invitation page queries only the occupied extension strings long
enough to choose the first available safe suggestion, starting at `101`; it
does not expose the occupied list or member names. The transactional uniqueness
constraint resolves simultaneous claims. A shared extension-rules package is
used by invitation claims, authenticated `*15` changes, storage, and Asterisk
rendering so familiar public emergency/crisis numbers cannot become party
destinations through another path.

Immediately after creating an invitation, the authenticated no-store party page renders both its HTTPS link and a PNG QR containing that exact link. RingRing builds the QR in memory with the same local renderer used for Linphone provisioning; the token is never sent to an image service. The encrypted host-only reveal cookie is consumed on that first page view, so neither the link nor QR is reconstructed on refresh. Scanning merely opens the ordinary invitation page: token hashing, expiration, atomic single use, CSRF, and safe extension selection remain unchanged.

A native phone may instead recognize that same exact `/join/{token}` URL and derive the same-origin `/api/v1/phone-invitations/{token}` endpoint. Its non-consuming `GET` returns only the already-visible party name and one advisory safe extension; it does not return the occupied list, member names, services, credentials, or host data. A bounded JSON `POST` supplies the normalized display name, chosen extension, adult classification, and device label. Member creation, independently encrypted SIP-device creation, and invitation consumption share the existing claim transaction. The successful response directly returns the validated SIP account and same-party call-menu snapshot, so this path creates no second undisclosed provisioning token. A uniqueness race returns `409` without consuming the invitation, while malformed, unknown, canceled, expired, and used bearer tokens collapse to generic unavailable responses.

The same host page counts active invitations through a party-and-host join without selecting their hashes. Its cancellation transaction first requires that exact host ownership, then deletes only rows for that party whose `used_at` is null and whose expiry has not passed. A concurrent claim and cancellation serialize through SQLite: cancellation removes the token before a claim can load it, or a completed claim sets `used_at` and is preserved. Used invitations, expired audit rows, members, devices, and routes are unchanged.

After an invitation claim commits, its already-private, no-store credential response also renders a first-call snapshot. The application had loaded the invitation's exact party before mutation; from that same party it reduces existing member rows to display label plus extension only when at least one device remains active. It separately reduces current service and party-key state to the short codes that the generated dialplan can actually route. `*14` appears only when the operator gate, party service, provider state, and newly claimed extension's adult classification are all ready. The invite form never receives the directory snapshot, and host-created/rotated setup cards and Linphone XML deliberately omit it. It is a setup aid, not a persistent or public directory.

## NAT and phone compatibility

Most devices will register outbound from home networks. PJSIP endpoints use symmetric RTP, forced response ports, rewritten contacts, server-relayed media, keepalives, and conservative codecs (`ulaw`, `alaw`, and optional `g722`). The setup UI will give exact registrar, username, secret, transport, and extension values instead of exposing Asterisk terminology.

The optional `make nat-smoke` gate exercises those settings without touching a family phone. Two SIPp clients run in separate private Linux network namespaces and reach an isolated Asterisk through distinct stateful SNAT identities. Each advertises an unreachable private SIP contact and private media address. The root-created generated-state bind is explicitly read-only and traversable by Asterisk's dropped UID even under an exact-candidate `umask 077`. Before SIPp begins its one-shot registration, the harness requires Asterisk to enumerate the exact disposable endpoint and both nested namespaces to reach it; missing configuration or unfinished network setup therefore cannot masquerade as a SIP authentication failure. The test then requires Asterisk to retain only the rewritten public contacts, route an authenticated party call, keep `direct_media=no`, and carry more than 100 non-SIP UDP media packets across each NAT in both directions. Exact media content is covered independently by the SIPp echo and official Linphone recording tests. This simulation materially exercises the NAT configuration but does not replace real household routers, carrier-grade NAT, Wi-Fi/cellular changes, or physical-device testing.

SIP TLS 1.2 on `5061/tcp` is the preferred signaling transport. Caddy remains the ACME owner: a root-only timer exports its storage, selects only the exact deployment hostname's certificate/key pair with at least one week remaining, validates the pair, and stages it in `/etc/ringring/tls`. Asterisk copies that pair into its private runtime directory and reloads PJSIP only when no calls are active. A two-day self-signed startup certificate keeps the transport structurally available while initial public issuance is pending, but public readiness fails until a trusted hostname-valid certificate is installed. UDP `5060` remains available for older adapters. Each transport has a separate Fail2Ban jail over the same Asterisk security events.

TLS protects SIP registration credentials and call-setup messages in transit. RingRing's current RTP remains unencrypted and server-relayed; enabling TLS does not make voice media confidential from the server or a network path that can observe RTP. The evidence and remaining physical-device gaps are tracked in [SIP TLS compatibility](SIP_TLS_COMPATIBILITY.md).

## Configuration flow

The database is authoritative. When a device or party setting changes, the app:

1. Validates the full desired configuration.
2. Renders party-scoped PJSIP and dialplan fragments into a temporary file.
3. Atomically replaces the generated files on a shared volume.
4. Requests a reload over private AMI.
5. Logs reload failures while preserving the database as the recoverable source of truth. One-time credentials already issued to a person stay visible even if a reload needs to be retried.

On startup, the app regenerates all telephony configuration from the database.

## One-time phone setup

The one-time setup screen keeps the universal registrar, username, password, extension, and transport fields for ATAs, desk phones, and arbitrary SIP apps. Current numeric credentials are visually grouped in threes and fours, with explicit instructions to omit the display spaces; the local copy helper and Linphone XML use the exact raw digits. The grouping never enters SQLite, Asterisk, a clipboard value, or provisioning XML. The screen also renders a Linphone-specific QR according to [Linphone's remote-provisioning format](https://wiki.linphone.org/xwiki/wiki/public/view/Linphone/Remote%20Provisioning/). No external QR or provisioning service receives the credentials.

The QR contains an HTTPS URL, not the SIP password. Its 32-byte random token is stored only as a SHA-256 digest, expires after 30 minutes, and is consumed transactionally by the first `GET`. `HEAD` does not consume it. The response decrypts only that device's SIP secret and returns a transient Linphone XML document with the generated username, extension, RingRing registrar, TLS port, and password; it contains no member name, party name, host data, or integration key. A second fetch receives a generic gone response. Rotation atomically replaces any prior link, while revocation and cascading device deletion remove it.

The vendor-neutral `/api/v1/phone-provisioning/{token}` route uses the same one-time boundary and returns a versioned JSON document. In addition to the single device's SIP fields, that document carries a bounded initial call-menu snapshot made only from active members in the device's party and currently routable service lines. The device's own member is omitted. Display labels and hidden dial targets are validated before serialization and again by the native app, which stores the snapshot with its SIP account in the device-only Keychain and places calls through named buttons without rendering the target. Manual dialing remains a secondary compatibility path.

After setup, `/api/v1/phone/state` authenticates the active device with its generated SIP username and decrypted password over HTTPS. The lookup is global only on the random SIP identity, then every directory, service, and live-call read is scoped to the resolved device's party and extension. The response can add `kind: call` buttons only for current ConfBridge rooms already reduced through the same party boundary; their targets are exact `*16{extension}` routes. The iOS app polls this small no-store snapshot while foregrounded and keeps its last fully validated copy across transient failures. Revocation or rotation invalidates both SIP and HTTP access without introducing another bearer credential.

Every binary embeds and serves the exact OpenAPI contract at `/openapi.yaml`; the canonical source and a client implementation checklist live in [Phone API](PHONE_API.md). The document is public and cross-origin readable, while invitation and credential endpoints deliberately remain non-CORS and same-origin-resource restricted. Released iOS setup cards keep using `/provision/ios/{token}` as a deprecated direct compatibility alias. It and `/api/v1/phone-provisioning/{token}` call the same validation and party-reduction code and atomically consume the same preconfigured-phone token, so a client must choose one rather than probing both. General invitation preview/claim has its own 48-hour token lifecycle described above. Canonical routes use bounded `application/problem+json` errors and never reveal why a bearer token is unavailable.

The reference server serves an Apple association document without a redirect at `/.well-known/apple-app-site-association`, restricted to `/join/*` for `7PTN7E8EDS.com.mcchord.ringring`. The signed iOS app carries the reciprocal `applinks:ringring.live` entitlement and handles the resulting browsing activity through the same strict link parser used by scan and paste. This two-way association covers only the reference hostname; self-hosted universal links require a separately signed app entitlement for that exact domain, though self-hosted HTTPS links continue to work through scan and paste.

Setup pages and provisioning responses are `no-store`, `no-referrer`, and `noindex`; token-bearing request paths for the XML, canonical JSON API, and compatibility JSON route are masked in application logs and share the provisioning rate limit. `HEAD` is refused before token consumption. The UI warns people to use an app-owned scanner instead of a normal camera/browser because an ordinary fetch would consume the link without configuring the app. A desktop `sip-linphone` handler and copyable, format-specific provisioning URLs are secondary paths.

For iPhone background delivery, PushKit supplies a 32-byte VoIP token after the account is configured. `PUT /api/v1/phone/push` uses that same device's HTTPS Basic credential, hashes the token for exact invalidation, encrypts the recoverable value with device-specific associated data, and stores it under the device foreign key. Rotation, revocation, deletion, app disconnect, PushKit invalidation, or a permanent APNs rejection removes the row. On an ordinary member dial, Asterisk passes the authenticated calling endpoint, target extension, and a fresh UUID to private FastAGI before `Dial`. FastAGI re-resolves the caller inside the stated party, selects only target-extension registrations, decrypts them, and sends APNs a production VoIP payload containing only the UUID and an empty `aps` object. The dialplan waits briefly only after APNs accepts a wake, then continues through the existing explicit same-party endpoint list.

The iOS PushKit callback immediately reports that UUID to CallKit with a generic RingRing label and completes the callback; it does not trust the push as call authorization. The app refreshes SIP registration, attaches the later Linphone invitation to the existing CallKit UUID, and only then replaces the label with the validated same-party directory name. Answer-before-registration is held locally until the SIP invitation arrives or a bounded timeout ends the CallKit call. This preserves SIP/Asterisk as the authoritative signaling boundary while allowing iOS to suspend the app. Force-quit launch behavior remains controlled by iOS and physical-device background/lock-screen acceptance is a release gate.

The manual setup sheet translates common ATA and SIP-phone labels into the six
RingRing values and can copy one value or a complete private setup note. The
core sheet remains usable without JavaScript. Its optional copy helper is one
small local asset pinned by the same SHA-256 digest in both Subresource
Integrity and Content Security Policy; executable security contracts reject
network, browser-storage, cookie, navigation, and logging primitives in that
asset. Copied text exists only in the browser and operating-system clipboard;
RingRing neither receives a copy event nor stores the plaintext credential.

The host can use the same one-time sheet to add another ATA, desk phone, or app to an existing member. The page makes the shared extension and unchanged existing phones explicit. This is not credential cloning: every added phone gets a different global SIP username, password, ciphertext association, provisioning token, presence state, readiness checklist, and revocation lifecycle.

The optional `make linphone-smoke` interoperability test packages the checksum-pinned official Linphone Python engine separately from RingRing. On a disposable internal Docker network, it serves one XML document generated by the same production function, supplies a disposable CA, enables Linphone's server-certificate and common-name verification, requires exactly one account and authenticated TLS registration, and independently asks Asterisk to confirm that contact is reachable. A second disposable member registers over UDP; Linphone then calls its extension through the real generated party dialplan while Asterisk keeps media server-relayed. The harness requires an established call, an allowed codec, more than 100 RTP packets in each direction, and a returned recording containing Linphone's 440 Hz file-backed input tone. Its read-only state, provisioning, and certificate bind roots remain traversable after the clients drop root even when the release checkout uses `umask 077`; the TLS private key remains root-only. It uses fixed smoke-only credentials, no production database or environment, and no host ports, and removes its containers, network, certificates, and generated state on exit. This proves the headless TLS provisioning, registration, mixed-transport party-call, and audio path, not mobile camera UX, push delivery, background ringing, or real NAT traversal.

The authenticated party page reads current PJSIP contact state through the same private AMI boundary. Asterisk emits one `ContactList` event per registered contact and a completion event; the app immediately reduces those events to a generated SIP username and normalized reachability state. Contact URIs, source addresses, ports, call IDs, and user-agent strings never enter the template or database. Results are not cached or exposed on public or invitation pages. A failed or slow AMI query produces an explicit “status unavailable” hint while leaving host controls usable.

Live presence and real-phone acceptance remain deliberately separate. The compatibility storage and host-scoped endpoint can retain three content-free confirmation timestamps for local `*10` echo, outgoing remote audio, and incoming remote ringing/audio, but the primary phone-book UI no longer presents a setup checklist. Live registration and active-call state are the useful everyday signals; physical acceptance stays an explicit release/deployment procedure. Revoked devices cannot be updated, credential rotation deletes the entire readiness row, and the device foreign key cascades deletion. No readiness data is inferred from AMI and no call-detail record is introduced.

Deletion follows the same source-of-truth rule. Removing a member cascades through its devices; removing a party cascades through invitations, services, members, devices, and encrypted party credentials. The app then reconciles the smaller desired configuration with Asterisk. If the private reload fails, the deletion remains authoritative in SQLite, the host receives an operator-retry warning, and the next successful reconciliation or app startup removes the stale generated route.

A party with an OpenAI project has an additional external boundary: the app retrieves and archives that project before deleting local party state. An archived response is accepted on retry, so a completed external archive followed by a failed local delete can safely be retried. An archive error fails closed and leaves the party, its members, and encrypted runtime key intact. A host account is deleted only after a transaction confirms that it owns no parties.

## Recovery boundary

Durable recovery state consists of the complete SQLite app-state directory plus both root-readable deployment environment files. The environment files are part of the recovery boundary because the application master key decrypts SIP and party service credentials; a database copy without that key is intentionally insufficient. Generated Asterisk configuration, synthesized voice cache files, and the copied SIP TLS certificate/key are derived state and are regenerated or reacquired after restore.

The checked-in backup workflow stops the only SQLite writer long enough for a consistent WAL-mode snapshot, restarts it, and verifies the copy without network access. The restore drill runs an extracted copy in a separate network-disabled container with no published ports, no organization admin key, and no AMI secret. It checks database structure, credential decryptability, application readiness, and telephony regeneration without mounting or replacing production state.

## Host authentication

Native host accounts use a case-insensitive username and an Argon2id password hash with a unique salt. Production signup additionally requires a deployment-level family access code, shared out of band with trusted hosts, so a public splash page cannot be used to create paid OpenAI resources anonymously. Eight random recovery codes are shown once, stored only as hashes, and rotated together after a successful password reset. Recovery invalidates every existing session.

Google OpenID Connect remains an optional integration, not a prerequisite for operating or joining RingRing.

## Special service lines

Every generated party context includes exact `0` and `*0` routes for the RingRing operator. A private FastAGI request carries the server-selected party ID, Asterisk’s authenticated endpoint identity, and one fixed reason selected by the dialplan: help, misdial, phone unavailable, or service unavailable. It never carries the dialed number or caller speech. The app validates the endpoint inside that party, loads the party’s enabled-service snapshot and encrypted runtime key, and asks OpenAI text-to-speech for a code-controlled explanation. The first successful operator playback for a member extension includes the AI-voice disclosure; later calls from any active device on that extension use the shorter disclosed variant. A single member-keyed timestamp records that fact without keeping a call, reason, destination, or audio history. Generated 8 kHz WAV prompts are cached by party, reason, disclosure variant, version, and service-update time. When the party key, provider, cache, or private app path is unavailable, the dialplan immediately assembles an appropriate explanation from bundled Asterisk prompts instead.

SIP does not tell RingRing that an analog handset is merely off hook: an ATA sends an INVITE only after it has a destination. A compatible adapter implements the idle-handset experience by using `0` or `*0` as its delayed off-hook, hotline, or warmline destination. The tested HT801 V2 uses `*0` in its documented **Off Hook Auto Dial** setting with an eight-second delay because that firmware special-cases a bare zero during delayed dialing; callers can still dial `0` or `*0` directly from any phone.

Every generated party context includes `*10`, an Asterisk-local echo test. It answers, beeps, and returns media and DTMF to the same authenticated caller until they press `#` or hang up. This proves a phone's microphone, speaker, negotiated codec, and both RTP directions without another member or external service.

Every context also includes `*15`, a voice-guided extension chooser. Asterisk passes the read-only PJSIP `CHANNEL(endpoint)` identity and the server-selected party ID to the private FastAGI listener; caller ID is never an authority. The caller enters 2–5 digits followed by `#`, hears the digits repeated, and must press `1` before anything changes. One database statement requires that exact endpoint to be active and attached to a member in that exact party, while the party/extension unique constraint resolves simultaneous or already-taken choices. The member's SIP username and encrypted password do not change.

After the database commit, the shared telephony reconciler serializes regeneration and asks Asterisk to reload. SQLite remains authoritative if that private reload fails, the failure is logged for operator repair, and startup reconciliation will retry it; an older RingRing binary can read the changed extension normally. The IVR uses only the bundled Asterisk prompts, does not record audio, and makes no external request.

An authenticated host can send an incoming setup ring to one active device they own. The store resolves the party, host, active device, generated SIP username, and extension in one scoped query without returning its encrypted password. The app rate-limits the host and device, rechecks current AMI contact reachability, and then uses Asterisk's documented [AMI `Originate` action](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Actions/Originate/) with an allowlisted `PJSIP/<generated username>` channel. Context, extension, priority, timeout, caller ID shape, variable name, and asynchronous behavior are fixed in code. After answer, an internal context disables its CDR, enforces a 20-second absolute limit, and assembles bundled prompts to say the extension. Party contexts do not include that context, and it contains no `Dial`, transfer, trunk, AGI, AudioSocket, URL, or shell primitive.

Each party controls its other generated routes from a dedicated settings page. `*11` uses Asterisk's local time playback, `*12` calls a private FastAGI service that combines Open-Meteo data with the party's OpenAI text-to-speech key, `*13` streams the host's selected catalog station through Asterisk, and `*14` connects the answered channel to the app's private AI AudioSocket listener. An enabled `*12` route passes Asterisk's authenticated endpoint, resolves it to one member, and reads only that member's weather coordinates. If the value is empty, the voice asks for exactly five DTMF digits, geocodes the U.S. ZIP, and atomically fills only that member before reading the first forecast in the same call. Phones on the same extension share the value; other members do not. A phone cannot replace an existing place; the host can set, change, or clear it from the member gear, while the party settings page can disable the route for everyone. Existing party-wide places are copied once to members present during the forward migration so an upgrade does not silently discard configured weather. The open-ended `*14` route additionally requires the deployment-wide adults-only gate; one-way weather speech remains independent. The public radio stream uses HTTP because Asterisk's `MP3Player`/`mpg123` path in the reference image cannot open HTTPS; it carries no credentials or caller data. A disabled optional service has no dialplan route.

Every party context ends with numeric and star-code fallbacks that answer and ask the RingRing operator to explain the misdial. Ordinary member routes also inspect `DIALSTATUS`: an offline, busy, or unanswered set of party endpoints gets the phone-unavailable explanation, while a completed conversation hangs up without the fallback. Private FastAGI failures and a radio player that returns unexpectedly receive the service-unavailable explanation. Exact member and enabled-service routes remain more specific than these patterns, every operator request stays inside the authenticated caller's party context, and bundled prompts remain behind every OpenAI-assisted route.

Weather setup and forecast audio are cached by party, while forecast audio also respects the settings timestamp; disabling the line takes effect before a cached file can be served. The ZIP remains DTMF: RingRing does not record or transcribe caller speech for setup. Radio state stores only one short station ID. Both the store and renderer resolve that ID through a fixed catalog of official SomaFM direct-player endpoints—[Groove Salad](https://somafm.com/groovesalad/directstreamlinks.html), [Drone Zone](https://somafm.com/dronezone/directstreamlinks.html), and [Deep Space One](https://somafm.com/deepspaceone/directstreamlinks.html)—and reject every unknown value. A host-provided URL therefore never reaches a network client or generated configuration. The catalog favors instrumental ambient programming but cannot guarantee live content; the host UI makes that boundary explicit and limits this integration to SomaFM's stated personal-listening use.

## OpenAI isolation

When `OPENAI_ADMIN_KEY` is configured, party creation provisions an OpenAI project, sets a monthly hard spend limit, creates a service account, encrypts the returned key once, and discards it from logs and responses. Provisioning accepts the limit only when OpenAI echoes the exact USD amount, monthly interval, and active `enforcing` status from its [project spend-limit endpoint](https://developers.openai.com/api/reference/typescript/resources/admin/subresources/organization/subresources/projects/subresources/spend_limit/methods/update). Runtime calls use that party key. The organization admin key is never used for model calls.

The host can choose any cent amount from `$0.01` through the deployment's `OPENAI_PARTY_SPEND_LIMIT_CENTS` ceiling; that setting is also the default for new parties. RingRing records one immutable pending amount and pauses new AI-powered weather and conversation authorizations before asking OpenAI to create or replace the limit. The ready amount changes only after the provider returns the same amount with enforcement active. A timeout, inactive or mismatched response, restart, or failed local completion leaves both the new spend state and the legacy OpenAI status paused. Retrying posts the exact pending amount again and cannot race it with a different value.

The authenticated host can replace that runtime key without replacing the party or project. RingRing uses OpenAI's supported [service-account key creation](https://developers.openai.com/api/reference/typescript/resources/admin/subresources/organization/subresources/projects/subresources/service_accounts/subresources/api_keys/methods/create) endpoint, encrypts the one-time value, and atomically records its key ID with a `rotating` state. AI-powered routes are disabled in that state. It then lists active project keys, keeps only the new key owned by the party's dedicated service account, and deletes every older key for that account. The ready state returns only after the new key appears in the provider list and every retirement succeeds. Key replacement and spend-limit reconciliation are mutually exclusive so their two external lifecycles cannot overlap.

The local update uses a compare-and-swap against the prior key ID, so concurrent host requests cannot both win. A timeout, restart, incomplete listing, or partial deletion leaves the fresh encrypted key authoritative and the party in a visible paused/error state. The host's retry resumes listing and retirement without creating another key. An unstored key from a lost compare-and-swap is deleted with a bounded cleanup request; the next successful rotation also removes any earlier orphan owned by the dedicated account.

Party deletion uses that administrator connection only to archive the party's project. Archival occurs before the local encrypted key and project identifiers are removed, and a local delete is refused if archival cannot be confirmed.

For `*14`, `AI_ADULT_ONLY_ENABLED=true` is an explicit deployment-wide operator gate. Startup closes stale durable settings unless that gate is true, and the reconciler independently filters the route while it is closed. A member chooses **Adult extension (18+)** only while claiming a new extension; the additive boolean stores no birthday or age. Existing members migrate to false. A party host can enable the line only after at least one adult extension exists.

At call time Asterisk passes the read-only authenticated PJSIP endpoint—not caller ID—to FastAGI. One party-scoped database query requires that exact active device to belong to an adult extension in the supplied party. Unknown, revoked, non-adult, and cross-party endpoints receive the same closed result. An allowed call receives a short-lived, one-use ticket keyed by a random call UUID. Asterisk then opens an [AudioSocket](https://docs.asterisk.org/Configuration/Channel-Drivers/AudioSocket/) connection containing that UUID. The app claims the ticket, rechecks both the operator gate and party, decrypts only that party's key, converts Asterisk's 8 kHz signed-linear audio to G.711 μ-law, and bridges it to OpenAI's server-side [Realtime WebSocket](https://developers.openai.com/api/docs/guides/realtime-websocket). The bridge checks the gate again before any provider connection. The connection sends a stable privacy-preserving safety identifier but no member name, raw SIP username, or extension. Neither the organization admin key nor another party's key enters the model call path.

RingRing omits input transcription, disables Realtime tracing, discards output transcript events, exposes no model tools, and stores no call content. It limits each call to three minutes by default and reserves only two simultaneous AI calls per deployment. Callers hear a generated adults-only AI/provider disclosure before live audio begins, without another form or keypad confirmation. Provider retention may apply. The operator can independently audit organization and party-project ZDR with `ringringctl openai-retention`; it is not a runtime precondition for this adult-only preview and remains required evidence before any future minor-facing design review.

## Growth seams

- A storage interface permits a later move from SQLite to PostgreSQL.
- A telephony reconciler isolates Asterisk configuration and reload mechanics.
- Service-line handlers are independent adapters.
- Static assets and templates are embedded for a single app artifact, while Caddy can serve them directly later if needed.
